# Sana memory, threads and context (RLM-style)

This is the design and the contract for Sana's persistent memory: chat threads and folders, durable
memories, and the context system the model uses to reach a user's history. It covers the backend
(`supabase/`) and the iOS client (`Strand/Coach`, `StrandiOS/Coach`). The macOS and Android coaches
(bring-your-own-key) are unchanged.

## 1. Why this shape

The coach's tool loop runs on the phone. The `coach` edge function holds the model key, relays model
calls, and stores conversation and memory. Wearable history lives on the phone: `Repository.days`
holds up to 4,000 days in memory. Conversations and memories live in Postgres.

The design borrows from Prime Agent and Recursive Language Models (RLM), adapted to this split:

| Prime / RLM idea | Sana equivalent |
|---|---|
| Context is a variable in the environment. The root sees its type and size, not its contents | A **context library manifest** in each turn's system prompt. It names what exists (earlier chats with dates and recent titles, saved memories by topic, wearable coverage) and which tool inspects each. It includes no contents. |
| Peek, grep and slice from code | **Typed inspection tools** with capped results: `search_conversations` (Postgres full-text, lexical and ranked), `read_conversation` (paged or around matches), `query_metric_history` and `find_days` (on the phone, over up to 4,000 days). |
| `llm_query` / `llm_batch` map over chunks | **`recall_context`** runs server-side in one round trip. Lexical candidates are partitioned into chunks. A cheap model maps over the chunks with bounded concurrency, then a reduce step merges the results only when needed. Depth is 1. Sub-model output is evidence, never the reply. |
| Ranked harness digest (top-k, lexical TF-IDF, "+N more, use search") | **Relevant memories** ranked per question (lexical relevance + importance + recency) replace "the first 8". The full set stays queryable with `get_memories`. |
| Incremental compaction (`UPDATE` summary merge, keep a recent tail) | **Per-thread rolling summary** built incrementally by a cheap model. The phone sends the newest 28 messages. When a thread is longer than that, the summary of older turns goes into the prompt. |
| Continual-harness refinement (review gate, JSON edit proposal, validated apply, audit) | **Memory curator** run after each turn by a cheap model. Ops are `add` / `update` / `confirm` / `retire`; "prefer no ops"; at most 4 per run. Server-side validation includes a near-duplicate merge. Every change goes to the audit table `coach_memory_events`. A periodic **consolidation** pass merges duplicates and retires superseded facts. |
| Side questions (`/btw`), with tools blocked and nothing written to history | Thread **titles**, **follow-up suggestions** and **starter suggestions** are side calls to the cheap model. They never enter the chat history. |
| Auxiliary model for background passes | `COACH_MODEL_UTILITY` (cheap, `reasoning_effort: none`, JSON) for titles, follow-ups, suggestions, summaries, curation and recall. The answer model is unchanged. |

**What we do not do:**
- We do not dump history into the prompt.
- Vector similarity is not the intelligence layer. Search is lexical (Postgres `tsvector`) plus structure: threads, dates, topics and summaries.
- No arbitrary model-written code runs per turn. A full Prime process costs about 16–21 s and about 100k tokens per run, which is far too slow for chat.
- Background work never spends the user's chat quota. It has its own utility budget.

## 2. Data model (`20261007160000_coach_threads_memory.sql`)

The migration is additive. All new tables are service-role only (RLS on, no client policies), use the
owner column `user_id`, cascade from `auth.users`, and are in `DELETION_TABLES`. Helper and trigger
functions live in schema `internal`. Public RPCs revoke everything from `public, anon, authenticated`
and are listed in `SERVICE_ONLY_FUNCTIONS`.

Also `unique (id, user_id)`. Indexes: `(user_id, pinned desc, last_message_at desc nulls last)`, and GIN on `search`.

### `coach_messages` (existing table, additive changes)
- `thread_id uuid null`, with a composite FK `(thread_id, user_id)` → `coach_threads(id, user_id)` on delete cascade. A message can never join another user's thread.
- `search tsvector generated always as (to_tsvector('english', left(content, 8000))) stored`, with a GIN index.
- Index `(user_id, thread_id, created_at desc, id desc)`.
- Trigger `internal.coach_messages_thread_stats` (after insert, delete, or update of thread_id/content) maintains `message_count`, `last_message_at`, `preview` and `updated_at` on the thread.
- **Backfill.** Legacy rows with `thread_id is null` are grouped per user into threads, splitting wherever two messages are more than 3 hours apart (the old "fresh chat each launch" sessions). Each group's title is the first user message cut to 60 characters, with `title_source='legacy'` and `origin='backfill'`. The backfill runs again harmlessly (only `thread_id is null` rows) and creates the trigger after it finishes.

### `coach_memory_items` (existing table, additive changes)
- New columns:
  - `updated_at`, `last_confirmed_at` (backfilled from `created_at`);
  - `confirmations integer default 1`;
  - `source text default 'tool'` (`tool | curator | user | legacy`);
  - `source_thread_id uuid null`;
  - `version integer default 1`;
  - `search tsvector` generated from `topic || ' ' || content`, with a GIN index.
- Topics accepted by the server are now `goal, injury, preference, achievement, lifestyle, routine, health, training, nutrition, sleep, general`. Before this change the tool advertised `routine`, but the server stored it as `general`.

### `coach_memory_events` (new; audit)
Columns:
- `id` bigint identity pk
- `user_id`
- `memory_id` uuid null
- `op`: `add | update | confirm | retire | merge | forget | evict`
- `actor`: `tool | curator | user | consolidator`
- `before` jsonb, `after` jsonb
- `thread_id` uuid null
- `reason` text ≤ 300
- `created_at`

Index on `(user_id, created_at desc)`. The newest 500 rows are kept per user.

### `coach_user_state` (new; one row per user)
Columns:
- `user_id` pk
- `suggestions` jsonb default '[]', `suggestions_fingerprint` text, `suggestions_at`
- `recent_searches` jsonb default '[]' (≤ 10 strings, newest first)
- `consolidated_at`, `consolidation_until` (lease)
- `updated_at`

### `coach_usage` (existing)
- Adds `utility_calls integer not null default 0`.
- `public.coach_take_utility_quota(p_user_id uuid, p_limit integer, p_units integer default 1) returns boolean` is atomic, like `coach_take_quota`, but it never touches `calls`.

### RPCs (service role only)
- **`public.coach_search_v1(p_user uuid, p_query text, p_limit integer default 20, p_exclude_thread uuid default null, p_from timestamptz default null, p_to timestamptz default null) returns jsonb`**
  - Builds an OR query from the distinct English lexemes of `p_query` (at most 16). If there are none, it returns empty arrays.
  - Ranking: `ts_rank_cd(search, q, 32)`, multiplied by a gentle recency boost `(1 + 0.25 * exp(-age_days / 90))`.
  - Snippets come from `ts_headline` with `MaxWords=26, MinWords=8, MaxFragments=1, StartSel=«, StopSel=»`, computed for the top rows only.
  - Returns `{terms:[text], hits:[{thread_id, message_id, role, created_at, rank, snippet}], threads:[{thread_id, title, last_message_at, rank, snippet}]}`. Thread rows match on title or summary.
  - `p_limit` is clamped to 1..50.
- **`public.coach_thread_claim_v1(p_user uuid, p_thread uuid, p_lease_seconds integer default 120) returns jsonb`**
  - Atomically takes the curator lease when it is free or expired.
  - Returns `{claimed, token, summary, summary_through, summary_messages, message_count, title, title_source}`, or `{claimed:false}`.
  - The curator publishes with a PostgREST PATCH filtered on `maintenance_token=eq.<token>`, which clears the lease. Zero rows back means the lease was lost.

## 3. Endpoints (`/functions/v1/coach/...`)

Authentication is unchanged: an installation bearer only. Every owner comes from the credential, never
from the body. **Every existing route keeps its request and response shape.**

### Existing routes, extended compatibly
- **`GET messages?limit=N`** (no thread): unchanged. Returns the latest N across the user, oldest first, skipping rows with a NULL `client_id`.
- **`GET messages?threadId=<uuid>&limit=1..200(default 60)&before=<iso>`**: one thread's page, oldest first. Returns `{messages:[…same shape + threadId], hasMore}`.
- **`POST messages`**:
  - Each message may carry `threadId`.
  - A thread that doesn't exist yet is created for the owner (`origin='app'`).
  - A thread owned by someone else gives 409 `thread_conflict`.
  - A message with no `threadId` comes from an old app build.
    - If the `clientId` already exists, it keeps its stored thread.
    - Otherwise it joins the user's newest `origin='legacy_client'` thread when that thread was active in the last 3 hours, or a new one is created.
  - The per-user prune is now **50,000** messages (it was 500), oldest first. Complete history is kept.
- **`DELETE messages`**: with no query, deletes all of the user's threads and messages (old "Clear conversation" semantics). With `?threadId=`, deletes that one thread.
- **`GET memories?q=&topic=&limit=`**:
  - Default ranking and the default limit of 50 are unchanged.
  - With `q`, rows are ordered by lexical relevance (§5) and then rank.
  - Rows gain optional fields `updatedAt`, `source`, `confirmations`.
  - `limit` can go up to 200.
- **`POST memories`** (`{content, topic?, importance?, threadId?}`):
  - Exact or near duplicates (§5) are confirmed instead of inserted. The response is `{memory, deduped:true}` and the row's `confirmations`, `last_confirmed_at` and max importance are bumped.
  - The store holds up to 200 memories (it was 50). Past that, the lowest-ranked memory is evicted, with an audit event.
- **`DELETE memories[/<id>]`**: unchanged, and audited (`forget`).

### New routes
| Route | Request | Response |
|---|---|---|
| `GET threads?limit=1..100(50)&before=<iso>&folderId=<uuid\|none>` | – | `{threads:[Thread], folders:[Folder], hasMore, nextBefore}`. Pinned first (first page only), then `last_message_at desc nulls last`. `before` pages the unpinned threads. |

| `DELETE threads/:id` | – | `{deleted:true}` |
| `POST threads/:id/title` | `{question, answer?}` | `{title, titleSource, generated}`. Only runs when `title_source` is `none`, `fallback` or `legacy`. Otherwise it returns the current title. |

| `POST context/thread` | `{threadId, query?, before?, limit?}` | `{thread:{id,title,createdAt,lastMessageAt,messageCount,summary}, messages:[{role,at,content}], window:'recent'\|'around_matches', hasMore}`. At most 8,000 characters of content; each message is cut to 1,500. |
| `POST context/recall` | `{question, threadId?, includeCurrent?, days?}` | `{answer, sources:[{threadId,title,at}], examined:{threads,chunks,subcalls,messages}, status:'answered'\|'nothing_found'\|'budget'\|'unavailable'}` |

Shapes:
- `Thread` = `{id, title, titleSource, folderId, pinned, origin, createdAt, updatedAt, lastMessageAt, messageCount, preview, topics, snippet?}`
- `Folder` = `{id, name, sortOrder, createdAt, updatedAt}`

**Manifest** (`POST context`):
```json
{
  "memories": [{"id":"…","content":"…","topic":"goal","importance":4,"createdAt":"…"}],
  "memoryCount": 52,
  "memoryTopics": {"goal": 4, "injury": 1},
  "thread": {"id":"…","title":"…","summary":"…","summaryMessages":24,"messageCount":40,"openLoops":["…"]},
  "library": {"threadCount": 37, "firstAt":"…","lastAt":"…",
              "recent": [{"id":"…","title":"…","lastMessageAt":"…"}]},
  "openLoops": [{"threadId":"…","title":"…","text":"…"}]
}
```
- `memories` holds up to 8 ranked for the question (§5).
- `thread` is null for a new chat.
- `library.recent` holds 5 entries, excluding the current thread.
- `openLoops` holds at most 3 entries, taken from other threads in the last 14 days.

**Quotas:**
- `chat` and `visual` take the existing chat quota (`COACH_DAILY_CALL_LIMIT`).
- Each cheap-model call takes one unit of `COACH_DAILY_UTILITY_LIMIT` (default 600). When the utility budget runs out, the deterministic fallbacks are used and nothing fails: title from the question, keyword follow-ups, local suggestions, summary skipped, recall returning `budget` with the lexical hits.
- `context`, `context/search` and `context/thread` make no model calls.

## 4. Cheap-model passes (`_shared/coach_curator.ts`, `coach_context.ts`)

All use `callUtility` (`_shared/coach_llm.ts`). Every call is configured the same way:
- model `cfg.models.utility`
- `stream:false`, `reasoning_effort:'none'`, `response_format:{type:'json_object'}`
- temperature 0.2–0.5, a small `max_tokens`, and a timeout of 8–15 s

`callUtility` takes a utility unit first, and returns `null` on any failure. The caller then uses its
deterministic fallback.

**Title**
- Input: the first question (≤ 600 characters) and the answer if present (≤ 1,200).
- Output: `{"title":"…"}`, 2–6 words.
- Sanitised: quotes, emoji and trailing punctuation stripped; whitespace collapsed; ≤ 48 characters; no "Chat about…".
- Fallback: the first 6 words of the question, capitalised (`title_source='fallback'`).
- Written with a PATCH filtered on `title_source=in.(none,fallback,legacy)`, so a user rename always wins.

**Follow-ups**
- Input: question, answer (≤ 3,000 characters), thread summary (≤ 600), questions already asked in the thread (≤ 12), and the top 4 memories.
- Output: `{"follow_ups":["…?","…?","…?"]}`.
- Validation:
  - each 8–80 characters and phrased in the user's voice;
  - not a normalised duplicate of an asked question or of another item;
  - no "as an AI" or model/vendor talk;
  - at most 3.
- The client stores them in the assistant message's `meta.followUps`.

**Suggestions (starters)**
- Inputs:
  - the phone's coarse `state` (§6.4);
  - up to 8 memories (goals, injuries, routines and preferences first);
  - up to 6 recent threads (title, date, open loops);
  - up to 10 recent user questions;
  - up to 5 recent searches.
- Output: `{"suggestions":[{"text","kind":"continue|state|goal|explore","thread_id"?}]}`, 4 items, each ≤ 64 characters, first person.
- Validation: dedupe, length, an existing `thread_id` only, and at most 2 `continue` items.
- Cache in `coach_user_state`, keyed by a SHA-256 fingerprint of:
  - the version;
  - the state;
  - the memory ids and versions;
  - the recent thread ids and `last_message_at`;
  - the recent searches;
  - the local day part.
- A fresh, matching cache entry younger than 12 h is reused. `refresh:true` bypasses the cache.
- Fallback: the client's `fallback` list (`source:'fallback'`).

**Maintain (summary + memory curator), per thread, idempotent**
1. Claim the lease with `coach_thread_claim_v1`. If it is busy, return `busy`.
2. Load the messages newer than `summary_through`, oldest first. If there are fewer than 2 new messages, or fewer than 4 when a summary already exists, skip the summary but still try consolidation.
3. Batch the new messages by size: ≤ 24 messages and ≤ 14,000 characters per batch, each message cut to 1,500 characters. Each batch folds into the previous summary (recursive summarisation, oldest batch first). At most 3 batches run per call; the rest are left for the next call.
4. Each batch's prompt also carries the candidate memories:
   - the 40 most lexically relevant to the batch;
   - plus every memory with importance ≥ 4;
   - as compact `id | topic | importance | content` lines.
5. The batch's output is:

   ```json
   {"summary":"≤1200 chars, third person, absolute dates (YYYY-MM-DD)",
    "topics":["≤6"], "open_loops":["≤3"],
    "memory_ops":[{"op":"add","topic":"goal","importance":4,"content":"User is …"},
                  {"op":"update","id":"<uuid>","content":"…","importance":3},
                  {"op":"confirm","id":"<uuid>"},
                  {"op":"retire","id":"<uuid>","reason":"…"}]}
   ```
6. Rules for memory ops:
   - only durable facts the **user** stated about themselves (goals, injuries, conditions, preferences, routines, equipment, schedule constraints, achievements);
   - never Sana's advice, daily metric values, or anything transient;
   - prefer no ops;
   - at most 4 ops per batch.
7. Validation:
   - op whitelist;
   - `add` content 8..400 characters, trimmed;
   - topic is coerced to the allowed set; importance is clamped to 1..5;
   - ids must be among the candidates sent;
   - `add` near-duplicates become `confirm`.
   Each applied op writes a `coach_memory_events` row (`actor:'curator'`, `thread_id`).
8. Publish the summary, topics, open loops, `summary_through`, `summary_messages` and `summarized_at`, fenced by the lease token.
9. **Consolidation.** It runs at most once every 72 h per user, under a lease in `coach_user_state`, when the user has more than 40 memories (or immediately above 120).
   - It sends the compact list of all memories.
   - The model returns `{"ops":[{"op":"merge","ids":[…],"content","topic","importance"} | {"op":"retire","id","reason"}]}`.
   - At most 12 ops are applied. A merge keeps the oldest id (version incremented, `confirmations` summed) and deletes the rest, each audited.

**Recall (`context/recall`, RLM map-reduce)**
1. **Candidates.**
   - Run `coach_search_v1(question, 40)`, excluding the current thread unless `includeCurrent`.
   - Group the hits by thread and keep the top 5 threads, scored as Σ rank × recency.
   - Add any thread whose title or summary matched.
   - If nothing matched, use the 5 most recent threads that have summaries; the status becomes `nothing_found` if there are none.
2. **Chunks (partition).**
   - Each chunk carries the thread title, its dates, its summary, and the matched messages with ±1 neighbour, each cut to 1,200 characters.
   - Chunks hold ≤ 10,000 characters. A thread with more matched material is split into several chunks; this is the recursive partition.
   - At most 8 chunks.
3. **Map.**
   - The cheap model reads one chunk at a time, at most 4 concurrently, 12 s each, 25 s overall.
   - Output: `{"relevant":bool,"notes":["≤5 bullets ≤220 chars, each with YYYY-MM-DD"]}`.
4. **Reduce.**
   - With 3 or fewer relevant chunks and ≤ 2,500 characters of notes, the notes are concatenated deterministically under `[title, date]` headers.
   - Otherwise one reduce call returns `{"briefing":"≤1400 chars"}`.
5. **Budget.** Every map and reduce call takes a utility unit. If the budget is exhausted, the response carries the lexical snippets with status `budget`.

## 5. Ranking and dedupe (deterministic, in `coach_llm.ts`)

- **Tokens:** NFKC-normalised, lowercased, ASCII word split, ≥ 3 characters, English stop-word removal, and light stemming (drop the suffixes `ing`, `ed`, `es`, `s`).
- **Memory relevance:**

  ```
  score = 3·lexical + importance/5 + 0.5·recency + 0.2·log(1+confirmations)
  ```
  - `lexical` is the TF-IDF overlap with the query (the question plus the thread summary), with IDF over the user's memories. It is normalised to 0..1.
  - `recency = exp(-days_since_last_confirmed/120)`.
  - With no query, the ranking falls back to importance and then recency.
- **Near-duplicate:** same topic family and (Jaccard ≥ 0.72, or containment ≥ 0.9) on token sets; or an exact normalised match in any topic.

## 6. iOS client

### 6.1 Pure, unit-tested logic (`Strand/Coach/`, compiled into `StrandTests`, must build on macOS 13)
- `CoachThreads.swift` contains:
  - `CoachThread`, `CoachFolder`, `CoachThreadPage`
  - `CoachThreadSections.sections(threads:folders:now:calendar:)`, which groups into pinned → folders → Today → Yesterday → Previous 7 Days → Previous 30 Days → Older
  - `CoachThreadTitle.fallback(from:)`
- `CoachThreadStore.swift`: `@MainActor final class CoachThreadStore: ObservableObject`.
  - Holds the thread list, folders and search results.
  - Caches to disk as JSON under Application Support `Coach/threads.json`.
  - Provides optimistic rename, move, pin and delete, plus `touch(threadId:preview:at:)` and `setTitle`.

- `CoachContextPrompt.swift`: builds the prompt blocks from `CoachContextManifest` plus local wearable coverage. The blocks are `REMEMBERED CONTEXT (from previous sessions):` (the existing header and line format), `EARLIER IN THIS CONVERSATION`, and `CONTEXT LIBRARY (queryable, not loaded …)` with the tool-use guidance.
- `CoachMetricHistory.swift`: `query_metric_history` and `find_days` over `[DailyMetric]`, with capped textual output.
- `CoachStarterSuggestions.swift`:
  - the coarse state snapshot for `POST suggestions`;
  - local fallback chips (`CoachSuggestions` bands first, then `CoachPrompts.suggestions`);
  - merge and dedupe.
- `CoachAPI.swift` gains the new endpoints. `CoachStoredMessage.threadId` and `CoachMessageMeta.followUps` are optional, so the existing JSON is unchanged.

### 6.4 Chat flow
1. **Launch.**
   - The thread list comes from the disk cache, then refreshes from the server.
   - If the newest thread was active on the same local day, it is reopened. Otherwise a new chat starts on the welcome screen.
   - All history stays in the sidebar.
2. **New chat.** A client UUID is created. Nothing is stored until the first message.
3. **Send.**
   - The user turn is appended.
   - For the first message, a title is requested in parallel (`POST threads/:id/title`).
   - `POST context` is fetched in parallel with the photo description, with a timeout of about 3 s that falls back to the cached memories.
   - The streaming tool loop is unchanged.
4. **Finish.** In order:
   - the turn goes into the outbox (with `threadId`);
   - the visual pipeline runs (unchanged);
   - follow-ups are requested (`POST followups`) and saved into `meta`;
   - `maintain` is fired;
   - the thread store is updated (preview, timestamp).
5. **Open a thread.** It loads the newest 60 messages; "Load earlier" pages back. Restored assistant messages show their stored visual and follow-ups.
6. **Starter suggestions.**
   - Local chips show immediately.
   - `POST suggestions` replaces them when it returns (cached server-side).
   - They are frozen for each new chat.
7. **Switching while generating.** Switching chats and New chat are disabled while a reply streams; Stop stays available. Visual tasks keep their own thread id and message snapshot, so a visual that finishes after a switch is still saved.

### 6.5 UI (`StrandiOS/Coach/`)
- **Header:** the sidebar button, "Sana" (unchanged), a subtitle (the thread title, otherwise "Your health assistant"), the New chat button and `BrandMark`.
- **Drawer:** `CoachSidebar` slides in from the leading edge over a scrim, at width `min(320, 84%)`.
  - Rows: search ("Search chats"), New chat, Folders (collapsible), date-grouped chats.
  - Context menu on a chat: Rename, Move to folder / New folder…, Pin/Unpin, Delete (with confirmation).
  - Footer: "What Sana remembers", a memory sheet with Forget and Forget all.
  - While the drawer is open, `NavRouter.coachSidebarOpen` suppresses `RootTabView`'s tab swipe.
- **Welcome and follow-ups:** they use the existing `CoachSuggestionStack` and `followUpList` visuals, fed by the dynamic lists.
- **Siri "Ask Coach"** now goes through `pendingPrompt` into a new Sana chat, the same way the Today launcher does.
